Networking

Modes

A_NET=offline     # or dhcp, wifi, static
offlinenothing explicitly configured - NetworkManager still auto-configures a wired link itself if one comes up
dhcpDHCP on whichever wired interface comes up
wifiwireless via NetworkManager, using the credentials given below
statica fixed address, gateway and DNS servers you specify

NetworkManager + nmtui is the installed system's whole networking story - DHCP, static config and wifi (through wpa_supplicant as its backend) all go through it, replacing what used to be an iwd/dhcpcd split between wireless and wired.

Wireless

A_NET=wifi
A_WIFI_SSID=your-network
A_WIFI_PSK=your-password
A_WIFI_IFACE=wlan0

A_WIFI_IFACE can be left unset - the installer picks whichever wireless interface actually exists rather than requiring you to know its kernel-assigned name in advance, which is not always stable across boots or hardware.

arctic-install writes what you give it straight into a NetworkManager keyfile connection at /etc/NetworkManager/system-connections/arctic-wifi.nmconnection (mode 600 - the PSK sits in it in plain text, same as any NetworkManager keyfile), so it's already there and set to auto-connect the first time the installed system boots.

Interactively, from the installed system, the same thing without touching the config - doas because changing a system connection needs root when polkit isn't installed (it isn't, on purpose - see reference):

doas nmtui

Pick "Activate a connection", choose the network, enter the passphrase. nmcli device wifi connect SSID password PSK does the same thing non-interactively, for a script.

Static configuration

A_NET=static
A_IP=192.168.1.50/24
A_GATEWAY=192.168.1.1
A_DNS="1.1.1.1 9.9.9.9"

A_IP takes CIDR notation directly rather than a separate netmask field. A_DNS accepts more than one resolver, space separated. This becomes an ipv4.method=manual NetworkManager keyfile connection, not a hand-written /etc/resolv.conf - NetworkManager owns that file once it's running and regenerates it from whichever connection is active.

The live/installer image's wireless is different, on purpose

The live ISO does not carry NetworkManager - it's a much bigger dependency tree (glib, meson, wpa_supplicant, newt for nmtui) than is worth hand-building into the earliest bootstrap stage just for an installer that runs once. Wired DHCP still comes up on its own on the live image (a small, live-only rc.d/network service - not the same thing as the installed system's networking, and installed systems never enable it). Wireless is manual there:

wifi-connect                                   scan, pick, connect
wifi-connect scan                              networks in range
wifi-connect list-networks                     the same list, names only
wifi-connect your-network your-password        join one without being asked

Run with no arguments it does the whole thing: it brings the interface up, scans (which takes a few seconds and says so), lists what is in range strongest first, asks which interface if there is more than one, asks which network, and reads the passphrase with the characters shown as asterisks. Then it associates, takes a lease, and prints the address, the gateway and the resolver it ended up with.

This needs iw, which is on the installation image. It was not, for a long time, and the consequence was that nothing on the image could list a network at all — the only way onto wireless was to type an SSID exactly right from memory.

The first two exist because the third needs a name you may not know: on a machine with no other way online, there was previously no way to find out what the network is called.

This drives wpa_supplicant directly (WPA2-Personal only - no 802.1X/enterprise on the live image, that needs a TLS backend that isn't built this early) and requests a DHCP lease once associated. Once you've installed and rebooted into the real system, that's where NetworkManager/nmtui takes over and the config above applies.

iw and wireless-regdb are installed onto the target system as well, as of a2.4 - not only the live image. A fresh install had wpa_supplicant with nothing that could scan for a network to give it, which is a closed loop: no network, no way to fetch iw, no way onto a network without it. wifi-connect works the moment a finished install boots now, and stays useful afterward as a repair tool if NetworkManager's own configuration ever needs troubleshooting from a shell.

MAC randomisation

A_MAC_RANDOMIZE=n

Set to y and NetworkManager presents a MAC address derived from the network (stable per-SSID, not traceable back to the adapter's real one) instead of broadcasting the hardware address every time it associates. Written as a global default in /etc/NetworkManager/conf.d/mac-randomization.conf, applying to every connection rather than just the one A_WIFI_SSID configures.

The firewall

A_FIREWALL=y

Installs and enables nftables with a default-deny inbound policy - established and related connections and loopback traffic are allowed, everything else inbound is dropped unless something else you installed (sshd, for instance) opens a hole for itself explicitly.

SSH

A_SSH=y
A_SSH_PASSWORD_AUTH=y    # set to n to require keys only
A_SSH_KEYS=""            # public keys to seed into the new user's authorized_keys

Enabling SSH also opens the corresponding hole in the firewall automatically when A_FIREWALL=y, rather than leaving you to notice the two settings need to agree with each other.

Why dbus used to fail

This is worth knowing even if you never hit it directly, because it shaped how service startup logging works today - the exact same failure mode now applies to NetworkManager instead of the iwd it originally happened with, since both register themselves on the system bus the same way at startup. The short version, described in full with the real error output at each stage in troubleshooting: /var/run did not exist (ell - the library both iwd and bluez are built on - looks there; dbus itself listens under /run), the netdev group iwd's D-Bus policy referenced did not exist (dbus silently rejects a policy naming an unresolvable group - NetworkManager's own policy references the same group now), and no machine ID had ever been generated (which dbus-daemon --system requires to start at all). None of the three produced an error anyone could see at the time, which is a large part of why it took real boot-log instrumentation, not guessing, to find them.
