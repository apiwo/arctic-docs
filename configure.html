Declarative configuration

The idea

A file describes the machine. A command makes the machine match the file. That is the whole model, and it is the same one NixOS uses — built here on top of an ordinary package manager rather than replacing it with a new one.

/etc/arctic/system.conf     what the machine is
arctic-rebuild               make it so

You do not alpm ins things onto a configured Arctic system as the normal way of working. You add a line to the file and rebuild. The difference is not stylistic: the file stays a complete, accurate description of the machine at all times, which is what makes rebuilding it identically elsewhere, diffing two points in time, or rolling it back possible at all. An imperative history of "I ran this, then I ran that" cannot be replayed or rolled back the same way a declared end state can.

system.conf

SYS_PACKAGES="
	git
	tmux
	ripgrep
	neovim
"

SYS_SERVICES="
	dbus
	NetworkManager
	sshd
"

SYS_PACKAGES is the complete list, not a list of things to add on top of whatever is already there. Deleting a name removes that package on the next rebuild, along with anything that was only ever installed as its dependency and is not needed by anything else still listed.

Only explicitly installed packages belong in this list. Dependencies are alpm's business to track — listing them yourself here is both unnecessary (alpm already knows) and wrong (it would make them look explicit, which changes what a later rebuild considers removable).

SYS_SERVICES works the same way for what runs at boot: the complete list of what should be enabled, not an addition to whatever is currently enabled.

arctic-rebuild

arctic-rebuild            make the system match the config
arctic-rebuild --dry-run  show what would change, change nothing

A rebuild diffs the file against reality and closes the gap:

:: recorded generation 4
:: reconciling against /etc/arctic/system.conf
  + install: ripgrep fd
  - remove: tmux
  + enable services: sshd
:: now on generation 5
:: rebuild complete

Removals go through alpm del+deps, so anything that was only pulled in as tmux's dependency and is not needed elsewhere goes too — while alpm's own protected-package list still refuses to remove the base system no matter what the file happens to say, so a typo that accidentally drops glibc from the list cannot actually take the machine down.

The first rebuild does not remove everything

An empty system.conf, read completely literally, would mean "this machine should have no packages at all" — which is never what an empty file actually means the first time you look at it. Instead, the first rebuild on a machine where the file is empty (or does not exist yet) seeds it from what is actually installed and enabled right now, and changes nothing on that run. You end up with an accurate starting file to edit from, rather than a destructive first surprise.

After an install this has already happened once — arctic-install writes system.conf from the install itself, so the seeding behaviour mainly matters for a machine that predates the declarative layer, or one where the file was deleted by hand.

Every rebuild is undoable

A rebuild records a generation before it changes anything, and another once it has succeeded. If an edit turns out to be wrong:

arctic rollback          go back one generation
arctic rollback 3        go back to a specific one
arctic diff 3 5          see exactly what changed between two

And if the result will not even boot, the recent generations are listed directly in the boot menu. Full detail in generations and rollback — this is the part of the declarative model that actually makes editing system.conf feel safe to do casually rather than something you approach carefully.

Services

Services are declared once, in SYS_SERVICES, regardless of which init is actually running on the machine. Arctic's own service definitions live in /etc/rc.d as a handful of shell variables per service, and are translated into OpenRC scripts, sysvinit entries, runit run files or dinit service files as needed — see init systems for exactly how that translation works and what it does and does not cover yet.

Directly, without editing the file — useful for a quick one-off change or for checking current state:

service list
service enable sshd
service disable sshd
service start sshd
service status sshd

service enable and the config file describe the same underlying state. Enabling a service by hand marks it enabled right now, but if system.conf does not also list it, the next rebuild will read the file, see that service is not declared, and turn it back off — because from the declarative system's point of view, an enabled service the file does not mention is exactly the same kind of drift as an installed package the file does not mention. This is intentional and is the entire point of a declarative system, but it is worth knowing about before it surprises you the first time a service you enabled by hand quietly disappears on the next arctic-rebuild.

System identity, users, and the nonfree flag

system.conf covers more than packages and services. Hostname, timezone, locale and keymap are reconciled the same way packages are — change the value, rebuild, it takes effect:

SYS_HOSTNAME="labbox"
SYS_TZ="America/New_York"
SYS_LOCALE="en_GB.UTF-8"
SYS_KEYMAP="us"

User accounts are declared too, one per line as name:shell:groups, but deliberately not symmetrically reconciled the way packages are: a declared user that does not exist yet is created on the next rebuild, but an account that already exists and is simply not listed is left alone rather than deleted. Automatically removing a user's account and home directory because a line was missing from a text file is a different order of consequence than removing a package, and this tool does not take that action without being asked more directly than an absent line — delete an account yourself with userdel if that is really what you want.

SYS_USERS="
	ray:/bin/zsh:wheel,users,audio,video
"

SYS_ALLOW_NONFREE gates the nonfree and alt-nonfree repositories the same way allowUnfree gates nixpkgs — no disables them (without uninstalling anything already pulled from them), yes enables them for future installs.

And after every successful rebuild, /etc/arctic/system.lock is written automatically: every explicitly installed package pinned to the exact version and release that is actually on the machine, the same reason a flake.lock sits next to a flake.nix. It is a record of what was actually applied, not something you edit — and, honestly, not yet something a rebuild reads back to pin against repository drift either. It exists today as an accurate record; enforcing it is a reasonable next step, not yet done.

What is still not declarative

Network configuration — which mode, wifi credentials, static addressing — is still set once at install time from install.conf and is not reconciled by arctic-rebuild. Changing it on a running system means editing the relevant files directly. There is also no concept of "outputs" the way a Nix flake exposes reusable modules and packages for other configurations to import: system.conf describes one machine, not a library other machines pull from. Both are known gaps, named here rather than implied to already work.
