Kernels

Choosing one

A_KERNEL=Arctic-base-kernel
Arctic-base-kernel the default. Linux 7.1.3, broad hardware support, most drivers as modules.
Arctic-kernel Linux 6.12 LTS with the ZEN patchset merged on top. See below.
Arctic-libre-kernel no binary blob loading paths, no nonfree microcode.
Arctic-small-kernel monolithic: no module loader at all, so no initramfs is needed either. Fast boot, fixed hardware.
Arctic-rt-kernel realtime preemption.
Arctic-hardened-kernel hardening-focused config options turned up.

More than one kernel can be installed on the same machine at once; the bootloader gets a separate entry for each. This is exactly the same mechanism generations use for a different purpose — see generations.

Arctic-kernel: a real fork, not a config change

Source at github.com/apiwo/arctic-kernel. Linux 6.12 LTS with the ZEN patchset merged directly into the tree, plus one small Arctic-authored patch on top of that.

What the ZEN merge brings:

  • PDS and BMQ alternate CPU schedulers, available but not enabled by default — see below
  • PCIe ACS override, useful for splitting IOMMU groups when passing a GPU through to a VM
  • ntsync — the Wine/Proton synchronisation primitives backport
  • vhba — a virtual SCSI host adapter, used for CD/DVD image emulation
  • inlined futex fast paths, and assorted scheduler/TCP/cpufreq tuning from the ZEN tree

The Arctic-authored patch on top raises the default readahead window to 512 KiB.

What it took to merge

ZEN is maintained against a moving 6.12 point-release line, and this fork pinned to a specific one (6.12.100) after the ZEN patchset itself had drifted through 83 upstream point releases (6.12.17 through 6.12.100) since the patches were originally written. Reconciling that gap by hand — not just re-running patch and hoping — is written down honestly in the repository's PATCHES.md, including the one hunk that genuinely did not apply cleanly and was dropped rather than forced: ZEN's AMD INVLPGB broadcast-TLB-flush backport in arch/x86/mm/tlb.c conflicted with upstream changes in a way that could not be resolved without risking subtle correctness bugs in TLB invalidation, so it was left out and the reason recorded rather than silently skipped.

Real build verification caught problems that inspection of the diff alone would have missed — a dangling goto label left behind from a partially dropped hunk, and a stale function-argument mismatch in a wholesale-new ZEN file (alt_core.c) that no shipped config even exercised, so it would have sat there silently broken until someone actually enabled CONFIG_SCHED_ALT. Both were found by actually compiling the tree, not by reading the patch.

The alternate scheduler

PDS and BMQ are compiled in and selectable (CONFIG_SCHED_ALT), but are not the default in any config Arctic ships — the mainline CFS-derived scheduler remains what actually runs unless you deliberately build a kernel with the alt scheduler enabled yourself. This is a conservative choice: PDS/BMQ have real advocates for interactive/desktop workloads, but making an alternate scheduler the silent default on a distribution most people will run unmodified is a bigger claim than "the code is there if you want it".

The Arctic kernel configuration

Both Arctic-base-kernel and Arctic-kernel start from a distribution baseline config and apply the same delta on top of it — the same options changed in both, for the same reasons, which is worth knowing since it means "which kernel" and "which config philosophy" are independent choices, not bundled together.

  • No BTF, no DWARF, no debuginfo. Across roughly 4,800 modules this costs hours of build time and hundreds of megabytes of image size for information almost nobody installing from an ISO needs.
  • No module signing, no lockdown. Nothing is signed at kernel build time; alpm's own per-file sha256 verification is the integrity mechanism actually in use.
  • Storage and bus controllers built in, not modular. SATA, NVMe, USB (xHCI/EHCI/OHCI/UHCI), virtio, SCSI. The initramfs (or the live squashfs's own early boot path) has to reach the boot medium before a single module can be loaded from it, so these specifically cannot themselves be modules.
  • Filesystems built in. ext4, btrfs, xfs, vfat, iso9660, squashfs, overlayfs — the live ISO mounts a compressed squashfs under a tmpfs overlay before any module is available to load, so all of that has to already be present in the kernel image itself.
  • Framebuffer and simpledrm built in, so a usable console exists before any real graphics driver has loaded.

Arctic-small-kernel goes one step further and disables the module loader entirely — everything it is able to do, it does without ever loading a module, and correspondingly needs no initramfs at all, trading flexibility for a genuinely faster boot on hardware you already know the shape of.

Building a kernel yourself

git clone https://github.com/apiwo/arctic-kernel
cd arctic-kernel
container/build.sh Default-config/config default bzImage modules

The build runs inside bubblewrap: the host toolchain is bound read-only, there is no network access during the build, and the only writable path is the build's own output directory. No docker or podman required or used.

Four ready-made configurations ship in the repository: Default-config, Hardened-config, Small-config, RT-config — matching the four flavours Arctic itself packages.

To build it specifically as an installable Arctic package, using Arctic's exact configuration rather than the repository's own Default-config, see building from source.

Microcode and firmware

A_MICROCODE=auto     # or intel, amd, none

auto reads vendor_id out of /proc/cpuinfo and installs intel-ucode or amd-ucode accordingly. Device firmware comes from the linux-firmware package, which Arctic-libre-kernel deliberately skips installing — choosing that kernel is specifically a statement about not wanting nonfree blobs on the machine, and pulling in linux-firmware anyway would quietly undo that.

Changing kernel later

The kernel is an ordinary package, so it is declared the same way any other package is:

SYS_PACKAGES="
	Arctic-kernel
	...
"
arctic-rebuild

Which means a kernel change is recorded as a generation like anything else, and a kernel that turns out not to boot is one entry away from being undone from the boot menu rather than requiring a rescue medium — see generations for exactly how that recovery path works.
