Ephemeral shells

Throwaway environments

A shell with packages available inside it that never touch the real system:

arctic-shell python rust
arctic-shell --keep ffmpeg
arctic-shell --network node

The environment is built in its own scratch root, entered with chroot, and torn down again when you exit — unless --keep was given. Nothing installed inside it is installed on the host machine itself. This is Arctic's rough equivalent of nix-shell: a way to have a toolchain available for one task without it becoming a permanent part of the system's declared package set.

Options

--keepdo not remove the environment on exit; reuse it the next time the same command is run
--networkleave networking reachable inside the chroot, off by default
-- cmdrun one command inside instead of dropping into an interactive shell

--keep is sticky in one specific direction: once an environment has been marked kept, a later invocation of the same environment without the flag does not silently un-mark it and delete it out from under you. Only an explicit --keep ever sets the marker; nothing un-sets it by omission. This was a real bug once — every invocation without the flag would quietly clear a previously kept environment's marker, so the very next cleanup pass would remove it — and the fix was specifically to make the marker write-only-on-request rather than reset-by-default.

Cleaning up

arctic gc

Prunes the package cache, orphaned dependencies, old generations beyond the configured keep count, and unused arctic-shell environments older than a week that were never marked kept.

Cleanup verifies, via /proc/mounts, that every bind mount belonging to an environment is genuinely unmounted before removing anything on disk. If that cannot be confirmed, the environment is left in place with a warning rather than removed anyway — recursively deleting a directory tree that still has something live mounted under it is exactly the kind of mistake that is not worth making twice, and this check exists specifically because of a real incident where an unsandboxed operation wrote into a mounted path it should not have been able to reach.

Recovering from a crashed session

A session killed outright — kill -9, a host crash — takes its bind mounts down with it; the exit trap that unmounts /dev, /proc and /sys before removing the environment only runs on a normal exit or a caught signal, never a -9. Nothing needs to be found by hand: every arctic-shell invocation sweeps the cache directory first, and an environment that is still mounted with no live process holding its lock file is unmounted (and, unless it was built with --keep, removed) before the new one is even built.
