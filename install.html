Install

One command

Boot the ISO. Wired networking comes up on its own via DHCP; for wireless, see networking for the full picture, but the short version:

wifi-connect YOUR-NETWORK your-password

Then edit the config and run the installer:

nano /etc/arctic/install.conf
arctic-install

No menus, no prompts, no arguments — arctic-install takes none. Which disk to use is something the config says, not something you type on the command line; there is no mount point to pass in and keep in sync by hand.

nano, vim and nvim are all on the ISO, along with JetBrains Mono and the Nerd Font symbol set so a terminal with icons works from the installer onward. vi is a symlink to vim — busybox ships its own minimal vi applet, but Arctic's live image replaces that symlink with the real editor rather than leaving both around under different names.

Checked, then confirmed, then installed

Before anything is written to disk, the whole config is validated in one pass. Either:

Config file accepted
  /etc/arctic/install.conf
  disk           /dev/sda (whole disk - everything on it is destroyed)
  filesystem     btrfs
  kernel         Arctic-kernel
  hostname       arctic
  desktop        xfce

Make these changes? [y/N]

or, if something is wrong, the full list of it, all at once, and nothing is touched:

Config file has errors
  /etc/arctic/install.conf

  A_ROOT_FS=reiserfs is not valid (try: ext4 ext3 ext2 btrfs xfs f2fs zfs)
  A_SNAPSHOT=btrfs needs A_ROOT_FS=btrfs (this config has ext4)
  A_ENCRYPT=y but A_ENCRYPT_PASS is empty

Nothing has been changed. Fix the config and run arctic-install again.

Every error is reported together rather than one per run. Warnings — a setting that will work but is probably not what was meant — are shown separately and do not block the install or the confirmation prompt.

To check a config without installing anything, skipping the prompt entirely:

arctic-install -n

or against a specific file:

arctic-install -n -c /path/to/some.conf

-f skips the confirmation prompt and installs immediately once the config is accepted — for scripted installs where there is nobody at the keyboard to answer it.

Choosing a disk

Two ways. Pick one — setting both is a validation error, since it would be ambiguous which one wins.

A whole disk

Arctic partitions and formats it: an ESP plus root on UEFI, a BIOS-boot partition plus root on legacy BIOS. Everything already on the disk is destroyed.

A_DISK=/dev/sda
A_ROOT_FS=btrfs

A_DISK_RESERVE leaves free space at the end of the disk instead of giving all of it to root, for a partition to add later:

A_DISK_RESERVE=100G

Partitions you made yourself

Partition with cfdisk, sfdisk or parted first — all three are on the ISO — then point Arctic at the results. Nothing is formatted unless you say so.

A_ROOT_PART=/dev/sda2
A_BOOT_PART=/dev/sda1
A_HOME_PART=/dev/sda3
A_FORMAT=n

With A_FORMAT=n Arctic mounts the partitions exactly as they are and installs into whatever is already there — which is the way to keep an existing /home across a reinstall of root. An existing btrfs partition is detected by its filesystem type and its @ subvolume layout is mounted, rather than the raw top level, so an install onto a btrfs root you made earlier lands correctly without needing to know the subvolume ID yourself.

Setting A_FORMAT=y with existing partitions formats them fresh but does not repartition — the sizes and boundaries you chose stay exactly as they are.

Filesystems

ext4the default — boring and reliable
btrfssubvolumes, snapshots, transparent compression
xfsgood with very large files
f2fstuned for flash storage
ext3, ext2for when you specifically need an older format
zfsneeds an out-of-tree kernel module; least tested path in the installer

btrfs gets four subvolumes by default: @ for root, @home, @snapshots and @log — a snapshot of root then restores without pulling your home directory or log history back with it. The list is A_BTRFS_SUBVOLS, so it can be changed; recognised names get mounted at a fixed place each (@home → /home, @cache → /var/cache, and so on), anything else is still created but left for A_MOUNTS to mount by hand. That split is also what A_SNAPSHOT=btrfs depends on:

A_ROOT_FS=btrfs
A_SNAPSHOT=btrfs
A_BTRFS_OPTS="rw,noatime,compress=zstd:3,space_cache=v2"

The mount options above are the defaults if you leave A_BTRFS_OPTS unset — zstd:3 compression is a reasonable middle ground between size and CPU cost, and space_cache=v2 avoids a slow free-space rescan on every mount that the v1 cache format is prone to.

A_BTRFS_NO_SNAPSHOT_CACHE=y adds a fifth subvolume, @cache → /var/cache, so package-manager and browser cache churn does not bloat every root snapshot taken afterward — shorthand for adding @cache to A_BTRFS_SUBVOLS directly.

Encryption

Full-disk LUKS2, applied under whichever filesystem you chose:

A_ENCRYPT=y
A_ENCRYPT_PASS=your-passphrase

An initramfs bundling cryptsetup and the dm-crypt kernel modules is generated automatically for an encrypted install — Arctic's kernel normally needs no initramfs at all, since storage and filesystem drivers are built in rather than modular, but an encrypted root is the one case where something has to run before root= means anything: the passphrase prompt. That prompt appears at boot, before anything else, reading rd.luks.uuid= off the kernel command line to find the right volume.

Works with every filesystem choice except zfs, which encrypts itself and would otherwise mean double encryption for no benefit.

Everything else

The shipped install.conf documents every setting inline, all commented out with its default shown, organised into sections. The full reference lists every variable alphabetically if you want the complete picture in one place; the highlights:

A_KERNELwhich kernel — see kernels
A_INITPID 1 — see init systems
A_DESKTOP, A_DM, A_AUDIO see desktops and audio
A_USER, A_USERPASS, A_ROOTPASS, A_LOCK_ROOT accounts; empty root password means the account is locked, same as A_LOCK_ROOT=y
A_SSH_KEYS, A_SSH_PASSWORD_AUTH authorized_keys contents, and whether sshd still accepts a password too
A_NET, A_WIFI_SSID, A_IP, A_MAC_RANDOMIZE see networking
A_HOSTNAME, A_TZ, A_LOCALE, A_KEYMAP, A_CONSOLE_FONT the usual system identity settings
A_SWAPnone, file, partition
A_ZRAM, A_ZRAM_SIZE, A_ZRAM_ALGO compressed swap in RAM, composes with A_SWAP rather than replacing it
A_PKGS, A_SETS, A_FONTS, A_SERVICES extra things to install and enable — A_SETS is whole categories (devel, net, media, office, virt, gaming, cli) rather than package names one at a time
A_PKGITinstall pkgit alongside alpm
A_MOUNTSextra fstab lines for storage beyond root/boot/home
A_HARDEN_TMPadds noexec to the tmpfs /tmp is already mounted as
A_POSTshell commands run inside the new system once everything else is done
A_CHROOT_SHELL, A_REBOOT drop into the finished system before showing the summary, or reboot straight into it

What the installer does, in order

Validate the config, print the summary above, and ask for confirmation. Partition (if A_DISK was set) or mount the given partitions. Unpack the base system. Install the chosen kernel and firmware. Install the init system if not busybox, translating services for it. Install everything else the config asked for — desktop, audio, networking tools, extra packages, package sets, fonts. Create accounts, write authorized_keys. Write /etc/fstab from the real mount table plus A_MOUNTS. Set up swap and zram. Install the bootloader — A_BOOTLOADER and the rest of the boot section are read straight off the same config, so this needs nothing further. Run A_POST. Seed /etc/arctic/system.conf from what was just installed, and record generation 1.

The fstab step is generated from /proc/mounts after everything is mounted, not reconstructed from the config. Whatever the install actually ended up with — including the case where formatting an existing partition was skipped and the real filesystem type differs from what was expected — is what gets recorded, with UUID= used throughout so a disk enumerated in a different order on the next boot does not break anything.

After the installer finishes, system.conf already describes the machine accurately and generation 1 is the machine exactly as installed — both of those already exist before the first arctic-rebuild ever runs, which matters because it means there is always something to compare against or roll back to, even on a freshly installed system nobody has touched yet.

Boot

In install.conf this section is last, on purpose — by the time these settings matter, everything above them has already decided what there is to boot.

A_BOOT_FW=efi          # or bios; detected automatically if unset
A_BOOTLOADER=limine    # or grub, for multi-booting alongside something that expects it
A_BOOT_MOUNT=/boot/efi
A_BOOT_TIMEOUT=3
A_KERNEL_ARGS=""
A_GENERATIONS=5

Firmware detection reads /sys/firmware/efi — if that directory exists, the machine booted UEFI and gets a FAT32 ESP; if it does not, BIOS and a small unformatted BIOS-boot partition instead.

A_GENERATIONS decides how many previous configurations appear as separate entries in the boot menu, each bootable on its own — see generations and rollback for what that actually does at boot time.

After the install

Reboot (A_REBOOT=y does this automatically, no prompt), or stay to poke around first with A_CHROOT_SHELL=y — /dev, /proc and /sys are bound into the new root for it, same as a real boot would have them. On first boot the account created is ready, root is locked if A_ROOTPASS was left empty (or A_LOCK_ROOT=y was set), and the network mode chosen is already configured. From here, ongoing changes go through system.conf — see declarative configuration.
