Init systems

Choosing one

Set it at install time:

A_INIT=busybox
busyboxthe default. busybox init, /etc/rc.boot, /etc/rc.d scripts. Nothing extra installed — this is the shape every service definition is written in, and what the others are translated from. It is the only init verified to boot every release so far.
initializationArctic's own fork of nitro: a supervisor that runs as pid 1, reads a directory of service definitions, and reports each service as it comes up. Installed as a package. Not the default as of a2.2 — a machine installed with it has frozen partway through boot and never reached a login; the cause is not yet diagnosed. Choose it deliberately, and be ready to boot busybox instead if it does not come up.
openrcdependency-based, from Gentoo. /etc/init.d, rc-update.
sysvinitthe traditional System V init. /etc/inittab, /etc/rc3.d.
runitsmall, direct process supervision. /etc/sv, sv up/sv down.
dinitdependency handling in a small footprint. dinitctl.
nitroa supervisor small enough to read in one sitting. Services are directories under /etc/nitro, all state is kept in RAM, and nitroctl drives it.
systemd-libreunits, journald, the usual suite, built without the nonfree firmware loading paths. Not packaged yet — see below.

Choosing anything other than busybox installs that init and its supervision tools, then translates every service Arctic enables into that init's own format. If the packages a choice needs are not actually available, the installer says so plainly and falls back to busybox init rather than quietly producing a machine that cannot boot at all.

Services are declared once

Arctic defines a service in /etc/rc.d as a handful of shell variables:

#!/bin/sh
NAME=bluetoothd
CMD=/usr/bin/bluetoothd
ARGS=""
BACKGROUND=yes

. /etc/arctic/svc.lib
svc_main "$@"

That is the single, authoritative definition. It gets read (not run) by arctic-init-setup, which extracts NAME, CMD, ARGS and BACKGROUND without executing the script, and generates the equivalent definition for whichever init is actually running — an OpenRC init.d script, a runit run file, a nitro service directory, a dinit service file, an s6 service directory, a systemd unit.

Shipping one definition and generating the rest, instead of hand maintaining eight parallel copies of every service, means adding a service to Arctic stays a one-file change, and no init can silently drift out of step with what the others do.

arctic-init-setup openrc              regenerate service definitions for OpenRC
arctic-init-setup runit --root /mnt   or write them into a target root, e.g. from the installer

A rebuild that changes the enabled service set automatically regenerates the definitions for whichever init the machine is actually running — this is not something you have to remember to do by hand after every rebuild.

Daemons versus one-shots

Not every service in /etc/rc.d is a long-running daemon with a CMD. network, nftables, fstrim and pipewire's bring-up define start()/stop() logic directly in the script instead, with no single process to supervise. The translation has to know the difference, and getting this wrong is exactly the kind of bug that leaves a machine silently missing something important: an earlier version of every generator here skipped services with no CMD entirely, which meant a non-busybox install would boot with no networking configured and no firewall enabled, with nothing in the output suggesting anything was wrong.

A service with a CMD becomes a properly supervised process under the target init. One without becomes a one-shot that calls the rc.d script's own start and stop directly — under nitro a service with a run script is supervised, one with only a setup script is a one-shot that stays up once it succeeds, and a disabled service gets a down file rather than being left out of the directory; under runit specifically, that means living in the stage-1 boot script rather than under /etc/sv, since runit's supervision model has no concept of "run once and exit successfully" the way dinit's scripted type or systemd's Type=oneshot do.

Daemons that would normally fork into the background are told to stay in the foreground when a real init is supervising them instead: dbus-daemon --system --nofork --nopidfile, sshd -D, crond -f, syslogd -n. Under busybox's own init none of this applies — the scripts run through svc.lib's own start-stop-daemon-based backgrounding instead, which is a different code path with different assumptions.

Where things land

busybox/etc/rc.d, enabled via marker files under /etc/arctic/services
openrc/etc/init.d, /etc/runlevels/default
sysvinit/etc/init.d, symlinked into /etc/rc3.d and /etc/rc5.d
runit/etc/sv, /etc/runit/runsvdir/default, one-shots in /etc/runit/1–3
dinit/etc/dinit.d, enabled ones linked into /etc/dinit.d/boot.d
systemd-libre/etc/systemd/system

Honest status

busybox init is what Arctic is actually built around, is what every service script in the tree is written and tested against directly, and is the only one that has been through a full install-and-boot cycle on real hardware as opposed to a virtual machine. openrc, sysvinit, runit and dinit all build correctly, package cleanly, and generate correct service definitions when tested through the translation logic directly — but they have had far less real-world use than busybox init has. If you are installing Arctic for the first time, use the default; if you are curious about one of the alternatives, treat it as something worth testing carefully rather than assuming parity with busybox's own path.

systemd-libre is not packaged at all yet — the dependency chain (udev, a full elogind or logind stack, and so on) is large, and building it correctly has not happened. It stays in the config because the intent is real, but selecting it today falls back to busybox init with an honest message explaining why, the same as any other choice whose packages are not available.
