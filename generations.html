Generations and rollback

What a generation is

A complete, self-contained record of what the system was declared to be at one moment: system.conf itself, the explicit package set with the exact version and release of every one of them, the enabled services, and which kernel was in use at the time.

Every arctic-rebuild writes one before it changes anything, and another once it has actually succeeded — so a rebuild that fails partway through still leaves behind a clean "before" record to fall back to. The install itself is generation 1, written by arctic-install at the end of the install, before you have ever run a rebuild by hand.

arctic generations

GEN   DATE                 PACKAGES SERVICES  DESCRIPTION
*5    2026-08-01 14:02:11  84       7         rebuild
 4    2026-08-01 14:02:03  82       6         before rebuild
 3    2026-07-31 09:14:55  82       6         rebuild
 2    2026-07-31 09:14:48  79       6         before rebuild
 1    2026-07-30 22:41:02  79       6         initial install

* = current

Rolling back

arctic rollback            go back one generation
arctic rollback 3          go back to generation 3 specifically
arctic diff 3 5            what changed between them
arctic-generation show 3   everything generation 3 recorded

Rolling back restores that generation's system.conf and then reconciles the running machine to it — the exact same reconciling operation an ordinary rebuild performs, just against an older file instead of the current one. Packages come back at the versions that generation recorded, and services return to the set it listed.

Switching to a generation is itself recorded as a new generation before it happens, so a rollback is also undoable — there is no dead-end state where you have rolled back to the wrong thing and now have no way forward. arctic rollback with no argument goes back exactly one generation from wherever the machine currently is, which covers the common case (undo the change you just made) without needing to look up a number first.

From the boot menu

A configuration that will not boot cannot be fixed from a shell you cannot reach, so the recent generations are listed directly in the bootloader:

Arctic Linux (recovery shell)
Arctic Linux (generation 4)
Arctic Linux (generation 3)
Arctic Linux (generation 2)

Choosing one of the generation entries boots with arctic.generation=N appended to the kernel command line. /etc/rc.boot checks for that argument very early, before any service starts, and reconciles the system to that generation if it is not already the current one — so booting that entry means the same thing as having run arctic-generation switch N before powering on, not just a differently labelled boot of the same broken system.

If the switch itself fails for some reason, the machine still finishes booting normally and reports the failure — an escape hatch that can itself get stuck is not an escape hatch, so this path is written to never abort the boot, only to log what went wrong and continue.

How many generations appear is controlled by A_GENERATIONS in install.conf, default 5. Setting it to 0 turns the boot menu entries off entirely, though generations themselves keep being recorded either way — this setting only controls the bootloader listing, not whether history is kept.

Housekeeping

arctic-generation list
arctic-generation prune 10     keep only the newest 10
arctic-generation delete 4
arctic-generation current      print the current generation's id

The current generation is never deleted, whether by an explicit delete or by prune trimming old ones — there is always at least the one the machine is actually running. arctic gc prunes generations as part of its wider cleanup, alongside the package cache, orphaned dependencies and unused arctic-shell environments.

Generations are not snapshots

Both exist, both are worth having, and they solve genuinely different problems.

Generation what the system was declared to be. Rolling back re-reconciles the machine to that declaration by reinstalling and removing packages as needed. Works on any filesystem, survives a full reinstall since it is just text, and is small — a handful of plain files per generation.
Snapshot the filesystem exactly as it literally was, restored file for file, byte for byte. Needs btrfs. Undoes things no package ever declared and a generation therefore has no record of — a config file you edited by hand outside of any package, something a build you ran directly wrote into /usr.
arctic generations     declared configurations
arctic snapshots       btrfs filesystem snapshots

alpm itself takes a snapshot before every install or removal whenever the root filesystem is btrfs, entirely independently of whether generations are in use — the two systems do not know about each other and do not need to.

Why this exists

Before generations existed, an arctic-rebuild that removed something important, or a bad edit to system.conf, had no clean way back short of a btrfs snapshot (if you had one and were on btrfs) or reinstalling. That is a real gap for anything calling itself declarative — NixOS's whole reputation rests on exactly this property, and a declarative system without a rollback path is really just an imperative system with extra bookkeeping. Generations close that gap directly: every reconciliation is bracketed by a recorded state on both sides, and the boot menu makes the worst case (an unbootable rebuild) recoverable without external media.
