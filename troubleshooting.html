Troubleshooting & reference

Start with the boot log

cat /run/arctic/boot.log
cat /var/log/boot.log     # from a previous boot

Every boot records, for every service: that it was considered, whether it started, and if not, its actual stderr output.

"failed to initialize dbus" from a D-Bus service

Anything that registers itself on the system bus at startup - pipewire, bluetoothd, a display manager - can hit any of these three, found one at a time by adding boot logging and reading what it said:

1. /var/run did not exist. A client built on ell (bluez, historically iwd) checks /var/run/dbus specifically, not /run/dbus. Fixed by adding /var/run -> ../run and /var/lock -> ../run/lock as merged-filesystem symlinks.

2. The netdev group did not exist. A D-Bus policy file granting members of netdev access to a bus name failed with Unknown group "netdev" - and dbus-daemon does not fail to start over this, it discards the policy and continues, so dbus looked healthy while the dependent service quietly couldn't claim its bus name. Fixed by adding netdev as a real system group.

3. No machine ID had ever been generated. dbus-daemon --system refuses to start at all without /etc/machine-id. Fixed by generating one on /etc/rc.d/dbus's first start.

service status dbus
ls -l /etc/machine-id
readlink /var/run
grep netdev /etc/group

A service is enabled but never starts

Check the boot log first - a service that's enabled but has no executable script at /etc/rc.d/<name> is reported explicitly (no executable /etc/rc.d/name) rather than silently doing nothing.

Chroot backspace moves the cursor instead of deleting

A target root has no terminfo database yet - the shell's line editor doesn't know what the terminal actually sends for erase, and backspace (which sends ^?) doesn't match what the editor expects (^H). arctic-chroot runs stty sane erase ^? explicitly before starting a shell, which needs no terminfo at all.

Ping fails with a permission error as a normal user

busybox's ping unconditionally opens a raw socket, which needs CAP_NET_RAW or root. Arctic ships busybox setuid-root with /etc/busybox.conf granting ping specifically to root and the wheel group - every other applet busybox marks BB_SUID_MAYBE (mount, findfs, traceroute) is explicitly denied in the same file, since an unlisted MAYBE-tagged applet stays fully root for any caller otherwise.

alpm environment variables

VariableDefaultWhat it does
ALPM_ROOT/work on another root instead of / (an extracted tarball, a chroot)
ALPM_CONF/etc/alpm/alpm.confalways host-absolute, even under ALPM_ROOT - a target's own copy is for its future use, not read during a cross-root install
ALPM_REPOD/etc/alpm/repos.dsame host-absolute rule as ALPM_CONF
ALPM_CACHE/var/cache/alpmdownloaded packages, fetched sources, build scratch
ALPM_YESunsetskip confirmation prompts
ALPM_FORCEunsetoverride a dependency or pkg.save[] refusal
ALPM_STYLEarcticoutput style - see packages

alpm-strap's whole reason for existing is that ALPM_CONF/ALPM_REPOD stay host-absolute under ALPM_ROOT by default - correct when a live Arctic session with real config at /etc/alpm is installing; wrong when the host is some other live Linux with no /etc/alpm at all, which is why it passes both explicitly.
