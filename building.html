Building from source

What you need

A Linux host with a working C toolchain, cmake, ninja, xorriso, mksquashfs, bubblewrap, and roughly 30 GiB of free disk space for a full build.

git clone https://github.com/apiwo/arctic-linux
git clone https://github.com/apiwo/arctic-linux-ports
cd arctic-linux
ln -s ../arctic-linux-ports ports

The ports tree lives in its own repository rather than inside the main one, so the main repository stays "the system" and not "the system plus several hundred recipes" — cloning it separately and symlinking it in is the expected setup, not a workaround.

Building

./build.sh                 the whole pipeline, start to finish
./build.sh rootfs iso      only run these specific steps

Steps, always in this order: fetch, kernel, rootfs, usable (the disk and wireless tooling layered on top of the base rootfs), pkgs (turn everything built into .alpmz and index the repositories), iso (master the bootable image). Every step checks whether its own output already exists before doing the work again, so a build that failed partway through can simply be re-run after fixing the problem, without needing to start the whole pipeline over from fetch.

To build one extra package directly into the repository, without running the whole pipeline:

build/arctic-sandbox build/build-batch.sh vim nano

Everything builds in a sandbox

Not a convention documented somewhere and hoped for — a rule the filesystem itself enforces. Every build step runs under bubblewrap, with the entire host filesystem bound read-only; only the build tree, the source tree and /tmp are ever writable from inside it.

build/arctic-sandbox --check

This exists because it went wrong once, badly. Arctic's glibc is configured with slibdir=/usr/lib for a merged-/usr layout, which means a recipe that forgets to pass DESTDIR during its own install step writes that glibc directly into the host's real /usr/lib — and every dynamically linked program on that host, including the shell you are typing in, stops working immediately. A note in a README saying "always use DESTDIR" was not sufficient the first time this happened; the filesystem itself now refuses the write instead of trusting every recipe to remember.

musl packages go through arctic-musl-sandbox instead of the plain one — same read-only-host guarantee, plus a working musl toolchain staged inside it. See musl for the details of how that injection is done without weakening the guarantee.

Testing what you built

build/arctic-qemu live        boot the ISO in QEMU
build/arctic-qemu live-uefi   boot it through OVMF instead of BIOS/SeaBIOS
build/arctic-qemu install     boot the ISO with a blank virtual disk attached
build/arctic-qemu boot        boot whatever was installed onto that disk
build/arctic-qemu wipe        delete the test disk and start over

Boot-testing is not optional for anything touching the boot path, the installer, or service startup — several of the real bugs described in troubleshooting produced no error at all in the build log and were only found by actually booting the result and looking at what happened.

The toolchain

glibc specifically cannot be compiled with clang — upstream glibc requires GCC — so build-rootfs.sh uses the host's own GCC as a stage-0 tool for glibc alone, once, and nothing else it might produce along the way is packaged or relied on further.

One detail worth knowing if you write or modify recipes: alpm-build exports pkgdir to every recipe but deliberately does not export srcdir. srcdir is autoconf's own reserved variable name for where a package's sources live, and exporting Arctic's own differently-meaning srcdir put a path autoconf never chose into the environment of every configure script a recipe runs — which silently broke any package whose top-level configure re-execs a nested one (vim's does exactly this: the top-level script is a two-line stub that runs src/configure), with no error message anywhere, just an empty ./configure --help output and a build that failed much later for a reason that looked unrelated.

Merged-/usr, and a mistake worth knowing about

/bin, /sbin, /lib and /lib64 are all symlinks into /usr, and /usr/sbin is itself a symlink to /usr/bin — a fully merged layout, not the traditional split. Setting that final symlink up correctly is less trivial than it looks: ln -sfn bin /usr/sbin run against a path that is already a real directory (which it will be, since packages install into /usr/sbin directly during the rootfs build) does not replace that directory with the intended symlink at all — it creates /usr/sbin/bin -> bin inside the existing directory instead, a symlink that points at itself, while /usr/sbin itself stays an ordinary unmerged directory the whole time. This shipped in a real image before it was caught: anything installed under /usr/sbin after that point (dhcpcd, among others) was reachable, but the tree was not actually merged the way every other piece of tooling assumed it was.

The fix moves anything already present in /usr/sbin into /usr/bin first, then replaces the now-empty directory with the symlink — and the same care is needed anywhere a package is unpacked onto the live tree afterward: a plain tar -xf of a package containing files under usr/sbin/ will, by default, replace an existing directory-symlink target with a real directory again on extraction, silently un-merging /usr a second time. mkiso's package-install step passes --keep-directory-symlink to tar specifically to prevent this.

Contributing

Pull requests are welcome and are read personally before merging. Package changes go through ports/manifest.tsv in arctic-linux-ports, not the main repository — edit the manifest, since recipes are generated from it and a hand-edited generated recipe will simply be overwritten on the next regeneration unless it also gets a recipe.local marker.

There is no logo yet. If you want to try making one, CONTRIBUTING.md in the main repository says exactly what is wanted.
