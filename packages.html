Packages (alpm)

alpm

Arctic's package manager, written specifically for this distribution. Binary packages are .alpmz files — a plain tar.xz archive containing a .PKGINFO metadata block, a .FILES manifest, and the actual payload rooted at /, so installing one is close to literally unpacking a tarball with bookkeeping on top.

alpm ins vim              install
alpm del vim              remove
alpm del+deps vim         remove, and anything only it needed as a dependency
alpm search editor        search names and descriptions
alpm info vim             what a package is, its version, its dependencies
alpm list                 everything currently installed
alpm files vim            every file a package owns
alpm owns /usr/bin/vim    which installed package owns a given file
alpm fetch all            refresh the repository indexes over the network
alpm upgrade              upgrade everything installed to the latest available
alpm system upgrade       all of the above, plus the kernel, the bootloader
                          and any pending fixes, in that order
alpm system fix           corrections that no version change would carry

alpm system fix

Some corrections do not move a package version: a default that turned out to be harmful, a service file that was wrong, a script that failed on some machines. An upgrade cannot carry those, because there is no newer version to upgrade to, and before this the only way one reached an installed machine was reinstalling it.

The fix repository is where they live. It is an ordinary binary repository — the packages in it are .alpmz files like any other, so applying a fix is still an install and the system stays binary — with one extra file naming which correction rides in which package, how much it matters, and what part of the system it touches.

alpm system fix               everything pending
alpm system fix bootloader    only what might explain a machine that will not boot
alpm system fix kernel
alpm system fix major         only the most serious
alpm system fix bugfix        both fix levels, and none of the changes

Every pending fix is listed before anything is installed, and applied fixes are remembered, so one is offered once and never again.

On a configured system, prefer editing system.conf and running arctic-rebuild over calling alpm ins directly — see declarative configuration for why. Using alpm directly still works exactly as shown above; the difference is only that the next rebuild will remove anything installed this way that the file does not also mention.

Building from source

Not every package has a binary built for it. When one does not, alpm offers to build it on the spot rather than simply failing:

alpm ins -s some-package    build from the port, even when a binary also exists
alpm build recipe           build a specific recipe file into an .alpmz directly

Recipes come from the ports tree, which is a separate host from the binary mirror and is never one of the repositories in /etc/alpm/repos.d. alpm reaches it through ALPM_PORTS, so "what can be installed" and "what can be compiled" are never the same list.

Undoing a transaction

Every install and removal is a transaction, and alpm rollback undoes one — the files it replaced go back, the files it added are removed, and the package database returns to what it described beforehand. A rolled-back install loses its database entry entirely; a rolled-back upgrade gets the previous version's entry back.

alpm rollback              undo the most recent transaction
alpm rollback 20260815-111525    undo a specific one
alpm log                   what has been done, and which transactions are on disk

On a btrfs root alpm also takes a filesystem snapshot before each transaction, which catches anything a package's install script did on its own — separate from the file-level rollback above.

How installs are reported

ALPM_STYLE in /etc/alpm/alpm.conf chooses the wording and layout. The resolver, the downloads and the progress are identical in all three; only the presentation changes.

arcticthe default — :: headings, a line per dependency
aptDebian's shape: Reading package lists..., a NEW-packages block, Get:1 <url> [size], Setting up <pkg> (<version>) ...
aerynAeryn OS's shape: a boxed, columnar transaction summary

Repositories

mainthe base system and the libraries it needs
basedesktops, X11, Wayland, and other larger stacks
extraapplications and general-purpose tools
kernelskernels, kernel headers, firmware
profilewhole-environment meta packages — a desktop, an audio stack, in one name
nonfree, alt-nonfree, multiliboff by default; opt in explicitly

Every one of these serves .alpmz binaries and nothing else. There is no "source" repository: a repository holds built packages, the ports tree holds recipes, and the two live on separate hosts — pkg-arctic.apiwow.net and ports-arctic.apiwow.net. Each index is generated from what the mirror actually holds, so a repository cannot advertise a package it cannot serve.

Configured per repository in /etc/alpm/repos.d/*.repo:

name = main
url = https://pkg-arctic.apiwow.net/ALL/main
enabled = yes
priority = 10

Browse the actual contents at pkg-arctic.apiwow.net and the ports/recipes at ports-arctic.apiwow.net. Packages and firmware larger than 25 MiB are served from GitHub Releases instead of the package host directly, since that is the free-tier file size limit on the hosting used — the listing marks those entries clearly rather than presenting a broken-looking local link.

Snapshots and rollback (package level)

On btrfs, alpm snapshots the filesystem before every install or removal:

alpm log                  every transaction, in order
alpm rollback              undo the most recent one
arctic snapshots           list them via the arctic umbrella command

This is a separate mechanism from generations, which record declared configuration rather than raw filesystem state — see generations for when you would reach for one over the other.

Ports

Every package in the repositories is generated from a single line in ports/manifest.tsv:

repo  name  version  buildsys  license  depends  makedepends  url  source  desc

gen-ports.py turns each row into a recipe using a template matched to the declared build system (autotools, cmake, meson, make, cargo, and so on). A package that needs something the template genuinely cannot express gets a hand-written recipe instead, with a recipe.local marker file placed beside it — that marker is what stops the next manifest-driven regeneration from silently overwriting the hand work, which happened more than once before the marker convention existed and is why it exists now.

Package and recipe changes go to arctic-linux-ports, not the main arctic-linux repository — edit the manifest there, not a generated recipe directly, unless it is one of the hand-written exceptions.

pkgit

pkgit can be installed alongside alpm:

A_PKGIT=y

alpm remains what the system itself is built, packaged and managed with — the declarative layer, the ports build pipeline, and the ISO itself all assume alpm specifically. This setting only adds pkgit next to it as an additional tool, not a replacement.
