musl

What musl is on Arctic

musl is an opt-in second C library installed at /usr/musl, sitting alongside glibc rather than replacing it. There is no separate musl edition of Arctic and no separate musl ISO — the same installed system can have both libraries present at once, and glibc remains what the base system itself is built against and what every binary package in the repositories links to.

alpm ins musl

Binaries are glibc

Every binary package in every repository is compiled against glibc, without exception. Trying to use one on a musl-only basis will not work — the binary needs glibc's dynamic linker and symbols, which will not be present if only musl is what you intended to rely on — and alpm is explicit about this rather than letting it fail with a confusing linker error:

Musl libc can only use source pkgs on Arctic.
Binaries are compiled via glibc.

The way through is building from source, which is the normal path for musl packages rather than a fallback for when something went wrong:

alpm ins -s some-package

Package naming

alpm's local package database is keyed by name globally, not separately per repository, so a musl build of something that already has a glibc package under the same name takes a -musl suffix instead — busybox-musl exists alongside busybox as two entirely separate installed packages. Packages with no glibc counterpart at all keep their plain, unsuffixed name.

The musl binary repository holds every package actually built this way. On the ports side there is deliberately no separate "musl" category — a recipe is a recipe, and whether a given build of it ends up linked against musl or glibc is decided by which sandbox runs the build, not by where the recipe lives in the tree.

Building musl packages

build/arctic-musl-sandbox --check
build/arctic-musl-sandbox build/build-batch.sh some-package

This is the musl counterpart to the ordinary arctic-sandbox used for every other build. Same guarantee — the host filesystem is read-only, only the build tree and /tmp are writable — plus a real, working musl toolchain staged at /usr/musl inside the sandbox with CC and MUSLGCC already pointing at it, so a recipe can simply reference $CC rather than hunting for a musl-gcc installation itself.

The two paths it needs that do not exist on the plain build host — /usr/musl itself and /usr/lib/ld-musl-x86_64.so.1, musl's hardcoded dynamic linker path baked into every binary musl-gcc produces — are injected using bubblewrap's read-only overlay feature rather than a writable tmpfs layered on top of those paths. That distinction matters: a tmpfs-based injection would make /usr/lib genuinely writable for any new filename, which quietly weakens the exact guarantee the sandbox exists to provide. The overlay approach stays read-only end to end, so a recipe that forgets DESTDIR still fails closed under the musl sandbox exactly as it would under the ordinary one.

Two gotchas worth knowing

Both of these were found by a build actually failing, not by reading documentation, and both will catch anyone porting something new to musl on this system.

An exported CC is not always enough. A Makefile that assigns its own CC = gcc internally wins over whatever the environment set — the assignment inside the Makefile is evaluated after the environment is read, not before. It has to be passed on the actual make command line to reliably win:

make CC="$MUSLGCC"

-static often fails outright. musl folds crypt(), libm and librt directly into its own libc, so there are no separate -lcrypt -lm -lrt static archives to link against the way there are under glibc. A build that unconditionally probes for and links those three libraries — busybox's own build does exactly this — fails under -static for a library that does not need to exist as a separate file, and works correctly linked dynamically instead.

Honest status

musl on Arctic is real and working but genuinely young: musl itself and busybox-musl build and package correctly and are verified working end to end, and the dedicated sandbox for building more musl packages is in place and tested. It is not yet a complete parallel system alongside glibc — most of the repositories have no musl counterpart built yet — and one real limitation is worth stating plainly: depend= in a recipe is metadata only. Nothing automatically stages a recipe's declared build dependencies onto the build host before running its build() function, so a musl port that needs another musl package present at build time currently has to stage it by hand inside the recipe itself, which is more manual work than the glibc build path requires.
